# **A Trust-Based Threat Model for the LLVM Compiler Infrastructure**

This document establishes a **trust-based threat model** for the LLVM compiler infrastructure, complementing the official security policy by defining trust boundaries, security responsibilities, and core assumptions for each component. It serves as a guide for developers, integrators, and security teams to understand the security posture of the toolchain.

LLVM's diverse ecosystem requires a multi-layered threat model, as a single security approach is insufficient for a toolchain that spans from source code parsing to machine code generation and runtime libraries. Instead of traditional frameworks like STRIDE, this document defines a **trust-based model** that classifies components based on their input assumptions and security responsibilities. This approach clarifies where security is enforced and where it is delegated, enabling developers and integrators to apply appropriate controls. The model categorizes components into three primary security postures:

| Security Posture | Description | Input Assumptions | Validation and Controls |
| :---- | :---- | :---- | :---- |
| **Active (Defensive)** | Explicit security controls with threat protection mechanisms | Expects potentially malicious or adversarial inputs | Performs significant input validation and sanitization with security hardening through runtime checks |
| **Passive (Pass-Through)** | Minimal security intervention | Trusts inputs are well-formed and benign | Limited validation; delegates security to external layers focusing on correctness and performance optimization |
| **Hybrid** | Selective security measures based on operational requirements | Generally trusts inputs but validates critical aspects | Internal checks for correctness and integrity while balancing between security and performance |

Most components within LLVM operate under a **Passive (Pass-Through)** or **Hybrid** security posture, prioritizing correctness and performance over defensive validation. They are built on the assumption that their inputs are well-formed and delegate security enforcement to other layers of the software stack. This trust-based approach allows for aggressive optimization but requires integrators to implement external security measures, such as input validation and environment hardening. To build a secure system with the LLVM toolchain, integrators must adopt a "defense-in-depth" strategy that includes sandboxing compilers, validating inputs, and deploying runtime protections.

# **Trust Boundaries of LLVM Components**
The LLVM compiler infrastructure implements a multi-layered trust boundary model that spans the entire toolchain ecosystem, from frontend parsing through optimization pipelines to runtime execution, with each component implementing distinct trust relationships based on its operational requirements. Understanding these boundaries is essential for security architects and integrators who need to implement appropriate controls and mitigations based on the trust model of integration.

## **Frontend Compilers**
Frontend components, including `Clang` and `Flang`, operate under a **passive** security posture with the fundamental assumption that both the host environment and input source code are trustworthy and well-formed. They are designed to trust their input and are not security sandboxes, meaning malicious code can lead to parser bugs, resource exhaustion, or other vulnerabilities.  **Crashes, excessive resource consumption, or other failures when processing maliciously crafted or malformed source code are not considered security issues** within the LLVM threat model. The responsibility for handling untrusted source code lies with integrators, who must implement appropriate protection, resource limits, and isolation mechanisms external to the compiler infrastructure. While developer tools in `clang-tools-extra` also trust their input, their operational context (especially for long-running servers like `clangd`) gives them a **hybrid** risk profile. They are not security-hardened, and integrators must protect against resource exhaustion and other attacks from malicious source code.

**Clang** implements a layered trust boundary system starting with the Source Code Input Boundary, where the lexer and parser provide error recovery without validating against malicious patterns. The Preprocessor Boundary encompasses macro expansion, include file processing, and conditional compilation while trusting source files and include paths. The Semantic Analysis Boundary represents the most significant internal trust boundary through the Sema component, which validates language semantics while trusting parsed syntax trees. The AST to IR Boundary completes the frontend's trust model by assuming semantic correctness from Sema during the code generation phase that translates Clang's AST to LLVM IR. This delegation model creates a chain of trust where each stage assumes the correctness of the previous one, culminating in the generation of LLVM IR that is considered well-formed and semantically valid by downstream components.

**Flang** mirrors Clang's approach with additional complexity from Fortran's unique features. The Fortran Source Boundary handles the legacy features and multiple standard versions inherent to Fortran. The Module Interface Boundary manages interface definitions and cross-module dependencies specific to Fortran's module system. The Array and Parallel Construct Boundary addresses Fortran's specialized array syntax and parallel constructs, creating trust boundaries around memory access patterns that are critical to Fortran's performance characteristics.

**Custom Integration Risks in Developer Tooling**: Frontend libraries are extensively integrated into developer tooling such as clang-tidy, clang-format, clangd (Language Server Protocol), and other code analysis tools. These integrations inherit the same trust assumptions and security limitations as the underlying frontend components. **Developer tools that process untrusted or user-provided source code face amplified risks** because they often run with elevated privileges, maintain persistent connections, or operate in shared development environments. Tool developers and integrators must implement additional safeguards including process isolation, resource monitoring, timeout mechanisms, and privilege separation to prevent malicious source code from compromising development environments. LSP servers are particularly vulnerable as they maintain long-running processes and may execute code analysis on every keystroke, creating opportunities for resource exhaustion or memory corruption attacks through carefully crafted input files.

## **Core Compiler Infrastructure**
The core compiler infrastructure operates on the assumption that its input data, such as LLVM IR or MLIR, is well-formed and trustworthy. These intermediate representations are expected to be generated by a trusted frontend and adhere to semantic correctness. While components like the IR verifier and dialect-specific verifiers check for structural validity, they do not defend against maliciously crafted IR designed to exploit the compiler's logic. Consequently, the integrity of the entire compilation process relies on the trustworthiness of the input data format; if the input IR is compromised, the correctness and security of the generated code cannot be guaranteed.

The core compiler infrastructure, including `LLVM` and `MLIR`, follows a **hybrid** security posture. While they feature active validation components, such as the IR verifier and dialect-specific checks, they are largely passive, trusting the semantics of the IR received from the frontend. Optimizers assume well-defined behavior and may remove security checks in code with undefined behavior. Post-link optimizers and analysis tools like `Polly` adopt a **passive** posture, trusting the binaries and IR they analyze. Across the toolchain's middle and back ends, a crash or incorrect output resulting from malformed input is generally not considered a security vulnerability.

**LLVM Core** operates through several critical trust boundaries that define its security posture. The most significant is the IR Input Boundary, where LLVM's IR verifier validates structural correctness but explicitly disclaims security validation, trusting the semantic correctness of input IR while ensuring well-formed SSA structures and type consistency. The Optimization Pass Boundary assumes well-formed IR and defined program semantics, with the PassManager coordinating these boundaries without implementing security isolation between passes. The Target Code Generation Boundary manages the transition from target-independent IR to machine code, trusting target descriptions and ABI compliance during instruction selection and register allocation. Finally, the JIT Compilation Boundary creates dynamic trust boundaries between compiled IR and runtime execution, requiring external enforcement of W^X memory protection and code signing through OrcJIT and ExecutionEngine components.

**MLIR** establishes trust boundaries through its dialect-centric architecture. The Dialect Input Boundary allows each dialect to define verification through dialect-specific validation, ensuring operations conform to their semantic requirements. The Conversion Boundary emerges during dialect-to-dialect transformations, where one dialect's semantics are mapped to another's while assuming correct conversion patterns and semantic preservation. The Operation Verification Boundary is maintained through individual operations implementing trait verification and invariant checking, trusting that operation definitions are correctly specified within their respective dialects.

## **Linkers**
**LLD** establishes trust boundaries around the linking process through several key interfaces. The Object File Input Boundary trusts object file structural integrity and symbol information while implementing format-specific parsing. The Symbol Resolution Boundary manages trust around symbol definitions, relocations, and inter-object dependencies during the complex symbol resolution process. The Script Processing Boundary handles linker scripts for memory layout and section placement, assuming script correctness and safety. The Output Generation Boundary completes the trust model during executable/library generation, managing section layout, program headers, and runtime metadata with trust in the overall linking process integrity. The `LLD` linker is also **passive**, relying on the assumption that incoming object files are well-formed.

## **Runtime & Standard Libraries**
All runtime and standard libraries operate under the assumption that the host process and its address space are trustworthy. The security of their in-memory data structures depends on the integrity of the execution environment. If an attacker can compromise the host process and arbitrarily modify memory, the security guarantees of these libraries are voided. Therefore, components like `libc`, `libcxx`, `libcxxabi`, and `libunwind` rely on the host process to maintain the integrity of their internal data structures.

The security posture of LLVM's runtime and standard libraries varies by component:

*   **`libc`**, **`libcxx`**, and **`libcxxabi`**: Implement a **hybrid** posture. While some functions are hardened against incorrect usage, most of the library trusts the caller to use the API correctly. Incorrect usage is generally not considered a security vulnerability unless explicitly documented as such.
*   **`compiler-rt`**: Adopts a **passive** posture, as it is intended for debugging and development, not for production security.
*   **`libunwind`**: Follows a **passive** posture, trusting the unwind information and stack frames it processes.
*   **`OpenMP`**: Operates with a **passive** posture, trusting the application code it executes in parallel.

**libc** establishes trust boundaries around fundamental C library functions. The File I/O Boundary trusts that file descriptors and streams are used correctly, without built-in defenses against path traversal or time-of-check-to-time-of-use (TOCTOU) attacks. The Memory Management Boundary trusts that callers correctly manage buffer sizes and memory allocation lifecycles to prevent overflows and memory leaks. The String and Data Manipulation Boundary assumes that functions like `strcpy` and `memcpy` receive valid pointers and buffer sizes, delegating security checks to the application. The System Call Boundary trusts that applications provide valid arguments for system-level operations, as it provides a thin wrapper over kernel interfaces without adding its own security validation.

**libcxx** defines trust boundaries for standard library features. The Standard Library Interface Boundary assumes that containers, algorithms, and utilities are used correctly according to C++ standards. The Memory Management Boundary trusts that applications will manage object lifecycles properly, while the Iterator Validity Boundary assumes iterators are used correctly, offering debug checks to help developers. The Allocator Boundary trusts that custom allocators adhere to standard requirements, as a misbehaving allocator can corrupt internal data structures.

**libcxxabi** is responsible for highly security-sensitive runtime trust boundaries. Its most critical boundary is Exception Handling, which governs stack unwinding, exception object management, and personality function execution. The RTTI Boundary handles runtime type information, trusting the integrity of vtable structures. The Memory Management Boundary oversees memory for exception objects, requiring precise heap management. The language-specific data area boundary trusts that exception-handling tables are well-formed, as corrupted data can misdirect the unwinding process.

**libunwind** functions at a low level with crucial trust boundaries for stack management. The Unwind Information Boundary trusts DWARF data for unwind information. While it performs some validation to prevent the most obvious crashes, it is not hardened against adversarily crafted DWARF sections, which could lead to hangs, excessive resource use, or incorrect unwinding in consumers like debuggers. The Stack Frame Boundary trusts that stack layouts are valid during traversal. The Platform ABI Boundary relies on adherence to platform-specific calling conventions. The Unwind Opcode Execution Boundary trusts that DWARF bytecode for unwinding is safe to execute, as it interprets this bytecode to restore register state.

**Compiler-RT** establishes trust boundaries related to runtime support and debugging. Its Sanitizer Runtime Boundary covers memory allocation, signal handling, and runtime checks, which are defined as debugging aids, not security features. The Builtin Function Boundary trusts that compiler-generated calls for arithmetic, memory, and floating-point operations use the runtime interfaces correctly.

## **Developer Tools & Debuggers**
**LLDB** operates with elevated privileges and establishes several critical trust boundaries. The Debug Information Boundary handles DWARF debug information parsing while trusting debug data integrity from binaries, with privilege management implemented in the debugger core. The Target Process Boundary creates the most critical trust relationship as LLDB attaches to and controls target processes with elevated privileges. The Remote Protocol Boundary extends this trust model across networks, assuming secure communication channels and authenticated remote servers. The Expression Evaluation Boundary enables runtime trust boundaries when executing user expressions within target process contexts, requiring careful privilege management.

The `LLDB` debugger operates with high privilege and follows a **passive** posture, trusting the debug information it consumes.

**BOLT** focuses its trust boundaries on binary analysis and rewriting. The Binary Input Boundary assumes well-formed ELF/MachO binaries and trusts their structural integrity during analysis. The Profile Data Boundary trusts that profile information accurately represents actual program behavior for optimization decisions. The Relocation Processing Boundary manages trust during binary rewriting, particularly around relocation processing and address space management, which are critical for maintaining program correctness after transformation.

Post-link optimizers like `BOLT` adopt a **passive** posture, trusting that the binaries they analyze are well-formed and not malicious.

# **Security Responsibilities at Trust Boundaries**
LLVM's trust boundary model is effective only when security responsibilities are clearly divided among three key stakeholder groups: **compiler developers**, **integrators**, and **end-users**. Each group has specific duties that align with LLVM's layered security approach and threat model classifications.

**Compiler Developer Responsibilities** should focus on ensuring the integrity and correctness of LLVM components according to their designated security posture. For components with an Active/Defensive posture, it is recommended that contributors implement robust input validation, handle memory safety within the module, and set secure default configurations. For Passive/Pass-Through components, their primary role is to document trust assumptions, minimal requirements for safe operation, secure integration guidelines, and uphold API contracts with a focus on correctness and security properties. For Hybrid components, developers should aim to strike a balance between implementing critical security validations and delegating other security concerns to external systems to maintain performance.

**Integrator Responsibilities** are recommendations for the secure deployment and configuration of LLVM toolchain components. It is recommended that integrators take responsibility for sandboxing compilation processes, particularly when handling untrusted source code with frontends like Clang and Flang. They should also aim to secure build environments, manage supply chain risks, set resource limits to guard against compiler bombs, and correctly deploy runtime protections such as ASLR, DEP, and W^X for JIT-compiled code. Finally, since build systems and third-party dependencies are considered **passive**, it is recommended that the integrator takes responsibility for securing the supply chain and build environment.

**End-User Responsibilities** are recommendations for the proper use of LLVM-generated toolchains and adherence to documented guidelines. End-users should not depend on undefined behavior for security guarantees, should implement their own application-level security controls, and correctly configure runtime security features. They are also encouraged to understand the limitations of development tools, keep their toolchain updated, and report any discovered security vulnerabilities.

# **Summary of Security Assumptions**
The following table summarizes the key security assumptions across different components and layers of the LLVM infrastructure. Integrators and developers must understand these assumptions to implement appropriate external security controls.

| Component/Layer | Key Assumption | Description |
| :--- | :--- | :--- |
| General | Source code is trusted | The compiler infrastructure operates on the premise that input source code is non-adversarial. Failures like crashes or excessive resource usage from malicious code are outside LLVM's direct security responsibility, shifting the burden of input validation and protecting the system integrator. |
| | Undefined Behavior (UB) is absent in secure code | LLVM's optimizers presume that secure code is free of undefined behavior. This allows them to eliminate code perceived as redundant, including security checks for null pointers or integer overflows, as these checks are tied to conditions that technically constitute UB. |
| | Build environment and supply chain are secure | The integrity of the build process, including third-party dependencies and the surrounding environment, is assumed but not verified by LLVM's build system. Responsibility for securing the software supply chain falls entirely on the integrator. |
| | Components operate without elevated privileges | LLVM components are designed for user-level execution. The security model assumes they are not run with unnecessary privileges (e.g., as root). When a tool like a debugger requires elevated access, it is assumed the integrator manages these permissions securely, often through isolated environments. |
| Frontend Compilers (`Clang`, `Flang`) | Inputs are well-formed and benign | Frontend components are designed for correctness and performance, not for security against hostile inputs. They operate on the assumption that source files, include paths, and flags are provided in good faith. |
| Developer Tooling (`clangd`, `clang-tidy`) | Inputs are trusted, but the execution context is high-risk | While inheriting the frontends' trust in source code, developer tools like `clangd` present a heightened risk due to their long-running, interactive nature. Integrators are responsible for mitigating resource-exhaustion attacks and other threats posed by malicious code in these environments. |
| Core Compiler (`LLVM`, `MLIR`) | Intermediate Representation (IR) is well-formed and semantically correct | The compiler's core components trust that incoming Intermediate Representation (IR) is semantically valid. While verifiers ensure structural integrity, they are not designed to detect or mitigate maliciously crafted IR that could exploit optimization logic. |
| Linkers (`LLD`) | Object files and linker scripts are trusted | The linker operates under the assumption that all its inputs, including object files, libraries, and linker scripts, are trustworthy. Its validation is limited to what is required for producing a correctly linked output. |
| JIT Compilation (`OrcJIT`) | External environment enforces memory protection | The security of JIT-compiled code hinges on the execution environment's ability to enforce memory protections. JIT components delegate the responsibility for implementing policies like W^X and managing memory permissions to the host application. |
| Runtime Libraries (`libc`, `libcxx`, `compiler-rt`, etc.) | Host process and execution environment are trusted | Runtime libraries presuppose that they execute within a secure, uncompromised process. Their guarantees become invalid if the host process's memory can be manipulated by an attacker. |
| | Callers use APIs correctly | These libraries expect callers to adhere strictly to API contracts, including providing valid arguments and managing memory appropriately. Deviations from documented usage are considered programming errors, not security vulnerabilities, unless explicitly stated otherwise. |
| Exception Handling (`libcxxabi`, `libunwind`) | Unwind information and runtime data structures are well-formed | The exception handling and unwinding systems rely on the integrity of runtime data structures like DWARF sections and LSDA tables. Corrupted or malicious data can disrupt control flow, leading to hangs or other failures. |
| Debuggers (`LLDB`) | Debug information is trustworthy | Operating with elevated privileges, the debugger trusts the integrity of the debug information (e.g., DWARF) it reads from binaries and does not attempt to defend against maliciously crafted debug data. |
| Post-Link Optimizers (`BOLT`) | Binaries and profile data are well-formed | Post-link optimizers assume that the binaries they instrument and the profile data they use for optimization are non-adversarial and provide an accurate representation of the program's execution. |

# **What is considered a security issue**
LLVM's security considerations span across multiple critical areas of the compiler infrastructure, runtime components, and supporting systems. The following sections detail specific categories of security issues that require careful attention and are considered reportable vulnerabilities within the LLVM project.

## **Compiler-Induced security vulnerabilities**
A compiler-induced vulnerability is a security flaw introduced by the compiler into a program built from well-formed source code that was previously secure and free of undefined behavior. LLVM's aggressive pursuit of performance can create a "correctness-security gap" where such issues arise. Language standards permit the compiler to exploit undefined behavior for optimization, and it is not expected to preserve security properties in code that relies on it. Such vulnerabilities typically stem from incorrect compiler optimizations or errors during code generation and pose a significant risk because they are invisible at the source-code level, silently affecting any application built with the compiler.

The most common source of these vulnerabilities is the optimization stage, where security-critical code may be eliminated. For example, optimizers might discard explicit security mitigations like bounds checks, null-pointer checks, integer-overflow checks, or memory-zeroing operations, deeming them redundant based on language rules. Optimizations can also introduce side-channel vulnerabilities by generating code susceptible to speculative execution attacks or creating data-dependent timing variations. Further issues can arise during code generation, such as selecting machine instructions with unintended side effects, insecurely spilling sensitive data from registers to the stack, or mishandling `volatile` semantics, thereby defeating security measures that rely on them.

These compiler-induced issues are formally recognized in industry standards like the Common Weakness Enumeration (CWE). For instance, the elimination of security safeguards such as bounds checks or sanitization routines is classified under CWE-733. Similarly, when optimizations alter security-critical control flow, they can introduce vulnerabilities categorized as CWE-670. The aggressive handling of undefined behavior, especially in integer or logical operations, can lead to errors covered by CWE-682. 

## **JIT compilation security issues**
Just-In-Time compilation presents unique security challenges due to its dynamic nature. Vulnerabilities in OrcJIT and other JIT components can lead to arbitrary code execution within the context of applications using LLVM's JIT infrastructure. Memory corruption issues in JITLink, particularly around symbol resolution and relocation processing, can allow attackers to inject malicious code into the JIT compilation pipeline. The dynamic nature of JIT compilation makes these vulnerabilities particularly challenging to detect and exploit, but also potentially more dangerous as they can be triggered at runtime.

The ExecutionEngine component must carefully manage privileges and permissions during JIT compilation. Security issues can arise when JIT-compiled code is able to escape its intended security boundaries, potentially leading to privilege escalation. This includes cases where JIT code can write to executable memory regions outside its allocation, bypass W^X protections, or manipulate the JIT compiler's internal data structures. Proper implementation of security features like Control Flow Integrity (CFI) and Write XOR Execute (W^X) protection is critical for JIT security.

## **Runtime library vulnerabilities**
Runtime libraries such as `libcxxabi`, `libunwind`, `libc`, and `libcxx` manage essential functions like exception handling, stack unwinding, and standard library operations. Given their role in managing fundamental aspects of program execution, such as control flow during exception handling, any vulnerabilities in these libraries can be extremely dangerous. Security flaws can appear in various ways, including spatial memory errors like buffer overflows, temporal memory errors like use-after-free bugs, or type-confusion vulnerabilities. Given their high level of privilege, these issues can be exploited to hijack control flow, especially during exception handling or stack unwinding. Other risks include thread safety issues in concurrent code and algorithmic complexity attacks leading to resource exhaustion. Incorrect or undefined use of library functions is not treated as a security vulnerability unless the documentation explicitly guarantees hardened behavior for that specific use case. 

## **Test code security risks**
The LLVM test infrastructure presents unique security challenges through its extensive test suites and infrastructure. The inclusion of untrusted binaries, potentially unwanted applications (PUAs), or malicious test cases in the test suite poses significant security risks, particularly because test files are often executed with elevated privileges during testing and continuous integration processes. Maintainers must actively discourage and prevent the inclusion of pre-compiled binaries, executable test cases, or untrusted code samples in the test infrastructure. Security vulnerabilities can manifest in various ways, including through embedded malicious binaries disguised as test cases, test scripts that download or execute untrusted code, test cases attempting privilege escalation, malicious code samples exploiting CI/CD environments, or test infrastructure that bypasses normal security controls.


# **What are not the security guarantees of LLVM infrastructure**

Understanding what LLVM does not guarantee is as important as understanding what it does. These non-guarantees are not security weaknesses but deliberate design choices that define the boundaries of LLVM's security responsibilities. By delegating certain security tasks to other layers, LLVM prioritizes correctness and performance while giving security architects the clarity to implement necessary protections externally. This clear separation of responsibility is a core tenet of LLVM's trust-based security model.

## **Input Validation and Sanitization**
LLVM operates on a fundamental trust assumption: **input source code is non-adversarial**. Consequently, it does not guarantee safe processing of maliciously crafted inputs. Issues like compiler bombs (exponential compilation time/memory), fork bombs in macros, and other resource exhaustion attacks are considered integration concerns, not compiler vulnerabilities. This design choice enables aggressive optimizations and clean architectural boundaries but requires integrators to implement protections like sandboxing and resource limiting when processing untrusted code.

## **Undefined Behavior Mitigation**
LLVM's optimizers assume that secure, well-formed code is free of undefined behavior (UB). This trust assumption is critical for performance but has significant security implications. Because UB is considered illegal in C and C++, the compiler is permitted to remove any code associated with it, including security checks that a developer may have written. This is not a compiler bug but a direct consequence of the language standards and LLVM's trust-based optimization model. Two common examples are:

*   **Null Pointer Check Elimination**: The compiler may discard null checks if it can deduce that a pointer will be dereferenced later, as dereferencing a null pointer is UB.
*   **Integer Overflow Check Elimination**: Because signed integer overflow is UB, optimizers may remove checks designed to prevent it, assuming that overflow will never occur in a well-formed program.

Developers must not rely on code that invokes UB for security guarantees. Instead, security-critical code must be written to be free of all undefined behavior.

## **Runtime library hardening**
LLVM's runtime libraries are not hardened against all potential threats. Specifically, the `compiler-rt` library and LLVM sanitizers are not considered security-sensitive. Since they are intended for development and testing, not for production builds, they are excluded from security hardening.

## **Supply chain integrity**
Build systems (cmake configuration) do not guarantee that third-party dependencies are free from malicious code or that the build environment is trusted. Supply chain integrity encompasses all aspects of the software development and build process that could introduce malicious code or compromise the integrity of the final software product. LLVM's build system focuses on correctly building the requested software but does not attempt to validate the integrity or trustworthiness of inputs to the build process. Third-party dependency validation is not performed by LLVM's build system. When the build process downloads or uses external libraries, tools, or data files, it trusts that these dependencies are legitimate and uncompromised. This trust extends to package managers, download mirrors, and other infrastructure used to obtain dependencies. Attackers who compromise this infrastructure can potentially inject malicious code into the build process.

NOTE: This threat model is defined for the LLVM open-source project, which treats public source code access as a cornerstone of its security verification process. As such, the security claims and responsibilities detailed in this document may not be directly applicable to closed-source products that incorporate or modify LLVM components.
