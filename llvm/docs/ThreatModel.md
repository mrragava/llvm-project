# **A Trust-Based Threat Model for the LLVM Compiler Infrastructure**

This document establishes a **trust-based threat model** for the LLVM compiler infrastructure, complementing the official security policy by defining trust boundaries, security responsibilities, and core assumptions for each component. It serves as a guide for developers, integrators, and security teams to understand the security posture of the toolchain.

LLVM's diverse ecosystem requires a multi-layered threat model, as a single security approach is insufficient for a toolchain that spans from source code parsing to machine code generation and runtime libraries. Instead of traditional frameworks like STRIDE, this document defines a **trust-based model** that classifies components based on their input assumptions and security responsibilities. This approach clarifies where security is enforced and where it is delegated, enabling developers and integrators to apply appropriate controls. The model categorizes components into three primary security postures:

| Security Posture | Description | Input Assumptions | Validation and Controls |
| :---- | :---- | :---- | :---- |
| **Active (Defensive)** | Explicit security controls with threat protection mechanisms | Expects potentially malicious or adversarial inputs | Performs significant input validation and sanitization with security hardening through runtime checks |
| **Passive (Pass-Through)** | Minimal security intervention | Trusts inputs are well-formed and benign | Limited validation that delegates security to external layers, focusing on correctness and performance optimization |
| **Hybrid** | Selective security measures based on operational requirements | Generally trusts inputs but validates critical aspects | Internal checks for correctness and integrity while balancing security and performance |

Most LLVM components operate under a **Passive** or **Hybrid** posture, assuming well-formed inputs and delegating security enforcement to other layers. This enables aggressive optimization but requires integrators to implement defense-in-depth measures such as sandboxing, input validation, and runtime protections.

# **Assumptions and Trust Boundaries of LLVM Components**

LLVM implements a multi-layered trust boundary model across its toolchain. The following table summarizes the key security assumptions, trust boundaries, and integrator requirements for each component. Understanding these is essential for implementing appropriate security controls. Note that the **security-sensitive** designation in the table indicates whether vulnerabilities in that component require coordinated disclosure through the LLVM Security Response Group.

| Component/Layer | Key Assumption | Description | Integrator Requirements |
| :--- | :--- | :--- | :--- |
| **General** | Source code is trusted | The compiler infrastructure operates on the premise that input source code is non-adversarial. Failures like crashes or excessive resource usage from malicious code are outside LLVM's direct security responsibility. | Input validation, sandboxing |
| | Undefined Behavior (UB) is absent in secure code | LLVM's optimizers presume that secure code is free of undefined behavior, allowing them to eliminate code perceived as redundant, including security checks tied to UB conditions. | Write UB-free security-critical code |
| | Build environment and supply chain are secure | The integrity of the build process, including third-party dependencies, is assumed but not verified by LLVM's build system. | Secure software supply chain |
| | Components operate without elevated privileges | LLVM components are designed for user-level execution and assume they are not run with unnecessary privileges. | Manage permissions securely and use isolated environments |
| **Frontend Compilers** (`Clang`, `Flang`) | Inputs are well-formed and benign | Operating under a **Passive** posture, frontend components are designed for correctness and performance, not for security against hostile inputs. Source files, include paths, and flags are assumed provided in good faith. **Not security-sensitive**: a maliciously crafted input file can cause arbitrary code to execute in LLVM because these parts haven't been hardened. Additionally, handling untrusted code usually also includes running utilities such as `make` which can more readily perform malicious things. | Sandboxing, resource limits, and isolation for untrusted code |
| **Developer Tooling** (`clangd`, `clang-tidy`, `clang-format`) | Inputs are trusted, but execution context is high-risk | Operating under a **Hybrid** posture, developer tools inherit frontend trust but present heightened risk due to their long-running, interactive nature. LSP servers are vulnerable to resource exhaustion. **Not security-sensitive**: vulnerabilities in `clangd` caused by untrusted inputs are not security-sensitive because these tools haven't been hardened against malicious inputs. | Process isolation and timeout mechanisms |
| **Core Compiler** (`LLVM`, `MLIR`) | Intermediate Representation (IR) is well-formed and semantically correct | Operating under a **Hybrid** posture, the compiler's core components trust that incoming Intermediate Representation (IR) is semantically valid. While verifiers ensure structural integrity, they are not designed to detect or mitigate maliciously crafted IR that could exploit optimization logic. Vulnerabilities caused by maliciously crafted bitcode or IR inputs are **not security-sensitive**. However, **code generation** issues where miscompilations make binaries significantly easier to exploit **are security-sensitive**. | None specified |
| **JIT Compilation** (`OrcJIT`) | External environment enforces memory protection | Operating under a **Hybrid** posture, JIT security hinges on the execution environment's ability to enforce memory protections. JIT components delegate W^X and memory permission policies to the host application. **Not security-sensitive**: vulnerabilities in the LLVM optimizer in a JIT caused by untrusted inputs are not security-sensitive because the JIT components haven't been hardened against malicious inputs. | W^X memory protection and code signing |
| **Linkers** (`LLD`) | Object files and linker scripts are trusted | Operating under a **Passive** posture, the linker assumes all inputs are trustworthy. Validation is limited to what is required for producing correctly linked output. | No security validation performed |
| **Runtime Libraries** (`libc`, `libcxx`, `libcxxabi`) | Host process is trusted and callers use APIs correctly | Operating under a **Hybrid** posture, runtime libraries presuppose execution within a secure process. API contract deviations are programming errors, not vulnerabilities, unless documentation states otherwise. **Partially security-sensitive**: vulnerabilities in correctly-used APIs are security-sensitive. However, if a user calls library functionality in an undefined or otherwise incorrect way, this will most likely **not** be considered a security issue, unless the documentation explicitly promises to harden or catch that specific undefined behavior or incorrect usage. | Incorrect usage is not a vulnerability unless documented |
| **Sanitizers** (`compiler-rt`) | Development/testing use only | Operating under a **Passive** posture, sanitizers and compiler-rt are intended for development environments, not production security. **Not security-sensitive**: these components are not meant to be included in production binaries and are meant to be used during development only. | Not for production security hardening |
| **Exception Handling** (`libunwind`) | Unwind information and DWARF data are well-formed | Operating under a **Passive** posture, exception handling relies on integrity of runtime data structures (DWARF sections, LSDA tables). Corrupted data can disrupt control flow. **Not security-sensitive**: the implementations of unwinding and exception handling are not hardened against malformed or malicious unwind or exception handling data. | Not hardened against malicious unwind information |
| **OpenMP Runtime** | Application code is trustworthy | Operating under a **Passive** posture, OpenMP trusts the application code it executes. | None specified |
| **Debuggers** (`LLDB`) | Debug information is trustworthy | Operating under a **Passive** posture with elevated privileges, the debugger trusts debug information (DWARF) integrity and does not defend against maliciously crafted debug data. | Manage elevated permissions securely |
| **Post-Link Optimizers** (`BOLT`) | Binaries and profile data are well-formed | Operating under a **Passive** posture, post-link optimizers assume binaries and profile data are non-adversarial and accurately represent program execution. | None specified |


# **What is Considered a Security Issue**

LLVM's security considerations span across multiple critical areas. The following table details specific categories of security issues that are considered reportable vulnerabilities. Note that whether an issue is security-sensitive depends on both the nature of the vulnerability and the component affected—see the security-sensitive designations below for guidance on reporting.

| Category | Description | Examples | Notes |
| :--- | :--- | :--- | :--- |
| **Compiler-Induced Vulnerabilities** | Security flaws introduced by the compiler into well-formed, UB-free source code | Incorrect removal of bounds, null, or overflow checks, side-channel introduction via speculative execution, mishandling of `volatile` semantics, and insecure register spilling | CWE-733 (eliminated safeguards), CWE-670 (altered control flow), CWE-682 (UB handling errors). Code relying on UB is **not** considered a compiler bug. Most miscompilations are not security-sensitive. However, miscompilations with clear indications that they make produced binaries **significantly easier to exploit** are security-sensitive and should be reported to the Security Response Group. |
| **Security Mitigation Defects** | Bugs or weaknesses in compiler-implemented security features that reduce or negate their protective value | Incomplete Retpoline coverage leaving unprotected indirect branches, CFI implementation gaps allowing type confusion bypasses, stack protector placement failures missing vulnerable functions, SLH (Speculative Load Hardening) not masking all speculative paths, shadow stack mishandling allowing return address overwrites, incorrect LFENCE placement in LVI mitigations, and BTI/PAC landing pad generation errors | When a security feature is explicitly enabled, defects that undermine its guarantees are **security-sensitive**. This does **not** apply to features that are disabled or unavailable. |
| **JIT Compilation Issues** | Vulnerabilities in dynamic compilation components | Arbitrary code execution in OrcJIT, memory corruption in JITLink (including symbol resolution and relocation), escaping security boundaries, and W^X bypass | Proper CFI and W^X implementation is critical |
| **Runtime Library Vulnerabilities** | Security flaws in `libcxxabi`, `libunwind`, `libc`, `libcxx` | Buffer overflows (spatial), use-after-free (temporal), type confusion, thread safety issues, and algorithmic complexity attacks | **Partially security-sensitive**: vulnerabilities in `libc`, `libcxx`, and `libcxxabi` affecting production binaries with correctly-used APIs are security-sensitive. Incorrect or undefined API use is **not** a vulnerability unless documentation guarantees hardened behavior. |
| **Test Infrastructure Risks** | Malicious content in test suites executed with elevated privileges | Embedded malicious binaries, test scripts that download or execute untrusted code, privilege escalation attempts, and CI/CD exploitation | Maintainers must prevent pre-compiled binaries and untrusted code samples |


As this security process matures, members of the LLVM community can propose that a part of the codebase be designated as security-sensitive (or no longer security-sensitive). This requires a rationale and buy-in from the LLVM community as for any RFC. In some cases, parts of the codebase could be handled as security-sensitive but need significant work to get to the stage where that's manageable. The LLVM community will need to decide whether it wants to invest in making these parts of the code securable, and maintain these security properties over time. In all cases, the LLVM Security Response Group should be consulted, since they'll be responding to security issues filed against these parts of the codebase.

**NOTE:** This threat model is defined for the LLVM open-source project, which treats public source code access as a cornerstone of its security verification process. The security claims and responsibilities detailed in this document may not be directly applicable to closed-source products that incorporate or modify LLVM components.
